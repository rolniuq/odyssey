Imagine a massive, meticulously organized filing cabinet in a busy office. You do not dump the
entire cabinet onto your desk when you need to answer a simple question. Instead, you hand a
specific request slip to the office clerk. You might ask for "only the names and phone numbers of
clients who live in Boston." The clerk goes to the cabinet, filters out the clients from other
cities, pulls out only the matching folders, and then copies down just the name and phone number
columns onto a clean sheet of paper to hand back to you. In PostgreSQL, the `SELECT` statement is
that precise request slip, ensuring you only receive the exact information you asked for without
disturbing the physical files.

## The precise version

In PostgreSQL, retrieving data is performed using the `SELECT` statement. When you execute a query,
the client application sends the SQL text to a PostgreSQL server backend process. This process
parses the query, and the **query planner** determines the most efficient way to access the physical
data stored on disk or cached in **shared buffers**.

To understand how data is retrieved, we must distinguish between two fundamental relational algebra
operations:

1. **Selection (Filtering Rows):** Restricting the rows returned by the query based on a conditional
   expression. In SQL, this is handled by the `WHERE` clause.
2. **Projection (Filtering Columns):** Restricting the columns returned by the query. In SQL, this
   is handled by specifying a comma-separated target list of columns immediately after the `SELECT`
   keyword.

The basic syntax of a query is:

```sql
SELECT target_list FROM table_expression WHERE condition;
```

During execution, the server process reads the table's underlying pages, filters out rows that do
not satisfy the `WHERE` condition, discards any columns not requested in the `target_list`, and
transmits the resulting **result set** back to the client over the network protocol.

## A hands-on walkthrough

Let's create a simple table representing weather observations, populate it with a few rows, and run
queries to see projection and selection in action.

First, we establish our table structure and insert some sample data:

```sql
CREATE TABLE weather (
    city      varchar(80),
    temp_lo   int,     -- low temperature in Fahrenheit
    temp_hi   int,     -- high temperature in Fahrenheit
    prcp      real,    -- precipitation
    date      date
);

INSERT INTO weather VALUES ('San Francisco', 46, 50, 0.25, '1994-11-27');
INSERT INTO weather VALUES ('San Francisco', 43, 57, 0.0, '1994-11-29');
INSERT INTO weather VALUES ('Hayward', 37, 54, 0.0, '1994-11-29');
```

### 1. Retrieve all columns and all rows

To see everything in the table, we use the asterisk (`*`) shorthand, which represents all columns:

```sql
SELECT * FROM weather;
```

**Expected Output:**

```text
     city      | temp_lo | temp_hi | prcp |    date
---------------+---------+---------+------+------------
 San Francisco |      46 |      50 | 0.25 | 1994-11-27
 San Francisco |      43 |      57 |    0 | 1994-11-29
 Hayward       |      37 |      54 |    0 | 1994-11-29
(3 rows)
```

### 2. Projection (Selecting specific columns)

To retrieve only the city names and their high temperatures, we list the columns explicitly. This is
highly recommended in production to save network bandwidth:

```sql
SELECT city, temp_hi FROM weather;
```

**Expected Output:**

```text
     city      | temp_hi
---------------+---------
 San Francisco |      50
 San Francisco |      57
 Hayward       |      54
(3 rows)
```

### 3. Selection (Filtering rows with WHERE)

To find only the records where it actually rained (precipitation greater than 0), we add a `WHERE`
clause:

```sql
SELECT * FROM weather WHERE prcp > 0.0;
```

**Expected Output:**

```text
     city      | temp_lo | temp_hi | prcp |    date
---------------+---------+---------+------+------------
 San Francisco |      46 |      50 | 0.25 | 1994-11-27
(1 row)
```

### 4. Combining Projection, Selection, and Expressions

You can also perform calculations on columns on-the-fly and rename the output columns using the `AS`
keyword:

```sql
SELECT city, (temp_hi + temp_lo) / 2 AS temp_avg
FROM weather
WHERE city = 'San Francisco';
```

**Expected Output:**

```text
     city      | temp_avg
---------------+----------
 San Francisco |       48
 San Francisco |       50
(2 rows)
```

## What this is NOT

It is easy to confuse the behavior of `SELECT` with other operations. Let's clarify what `SELECT` is
not:

| Concept                   | SELECT                                                              | What it is NOT                                                       | Why the difference matters                                                                           |
| :------------------------ | :------------------------------------------------------------------ | :------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------- |
| **Data Mutation**         | Read-only operation. It never alters the data stored on disk.       | `UPDATE` or `DELETE`                                                 | You can run `SELECT` safely without fear of corrupting or losing production data.                    |
| **Client-side Filtering** | The server filters rows _before_ sending them over the network.     | Fetching everything and filtering in code (e.g., JavaScript/Python). | Server-side filtering utilizes indexes and prevents network bottlenecks.                             |
| **Schema Modification**   | Modifies the presentation of the output (e.g., renaming with `AS`). | `ALTER TABLE`                                                        | Renaming a column in a `SELECT` statement only affects the current result set, not the table schema. |

## The diagram matters

Understanding the flow of a `SELECT` statement is the foundation of database performance tuning.
When you write a query, PostgreSQL does not execute it in the exact order it is written.

For example, in a query containing `SELECT city FROM weather WHERE prcp > 0;`, the server must first
locate the table (`FROM`), filter the rows (`WHERE`), and only then discard the unwanted columns to
return the final list (`SELECT`).

{/* DIAGRAM: A flowchart showing: 1. Parse Query -> 2. Plan Scan (FROM) -> 3. Evaluate Filter (WHERE) -> 4. Project Columns (SELECT list) -> 5. Return Result Set. */}

By mastering this pipeline, you unlock the ability to read execution plans (`EXPLAIN`), design
efficient indexes that speed up the `WHERE` clause, and avoid the performance pitfalls of retrieving
unnecessary columns.
