## The one question this page answers

When you write a query and run it, you might imagine the database \"doing\" it line by line, the way
you typed it. **That picture is wrong.** Behind the scenes, PostgreSQL treats your query like a
_program to compile_, not a to-do list.

There are three clear stages, and they happen in a strict order:

1. **Parse** — check the grammar, turn text into a structure.
2. **Plan** — decide the cheapest way to do it (no data touched yet).
3. **Execute** — finally open the tables and move the rows.

Everything important about PostgreSQL later (why indexes matter, what `EXPLAIN` shows, why a `JOIN`
order changes speed) grows from these three.

## Start with an analogy

Think of asking a chef to make a dish from a recipe you wrote.

- **Parse** is the chef checking the recipe is actually written validly — \"flour, eggs, salt\" —
  and writing notes on the margins. No food touched yet.
- **Plan** is the chef calculating: \"I'll start the oven first, whisk eggs while it heats, because
  the oven is the slowest.\" Choosing the order. Still no food touched.
- **Execute** is the cook actually opening the fridge and cooking.

The _chef only cooks once the plan is chosen._ And the choice of plan — turn the oven on early vs.
late — can change how fast your dinner comes out. That's exactly what the planner does with your
query.

## The three stages, honestly

The animation above is the whole idea. But let's make each box precise, because the precise
definition is what survives the quiz.

### Parser — grammar, not truth

PostgreSQL takes the characters of your query and checks: are the _words_ valid, are the _places_
right, are the punctuation balanced? The result is a structure called a **syntax tree**. Crucially
the parser does **not** know your data — it has never looked at a row. It has only checked the
grammar.

### Planner — choosing, not doing

Now PostgreSQL takes that syntax tree and asks: _given that tree, what is the cheapest real set of
steps to get the answer?_ There are usually many ways:

- read the whole table row by row
- use index A
- use index B
- build a temp list, sort it, etc.

The planner estimates a **cost** per option and picks the cheapest. It never touches a row. It's
pure math on the _shape_ of the query and the metadata it has about your tables. For now: **planner
= decision-maker, zero data.**

### Executor — the only place work happens

Only now does PostgreSQL open the tables, read pages, apply your `WHERE`, join rows, sort, and
return you the result. All those rows you get back exist because of a single engine actually
stepping through the chosen plan.

When you see a slow query, nine times out of ten it is the executor being asked to do something
expensive — which traces back to a plan the planner chose. Fix the plan, and the executor has less
to do.

## What this is NOT

| Misconception                                   | Truth                                                                        |
| ----------------------------------------------- | ---------------------------------------------------------------------------- |
| \"SQL runs the way I typed it\"                 | SQL is _compiled_: parse → plan → execute. Data only moves in the last step. |
| \"The parser reads my data\"                    | The parser only validates grammar. Zero data.                                |
| \"The planner runs the query to compare speed\" | The planner _estimates_ costs from statistics; it never experiments.         |

## Why this matters for the rest of the trip

Everything you will do from Lesson 2 on — single-table queries, indexes, joins, `EXPLAIN`,
transactions — hangs off the same skeleton:

**text → syntax tree → chosen plan → actual execution → your rows.**

Keep the skeleton, and later lessons are just tattooed variations on it.
