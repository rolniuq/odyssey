## The one question this page answers

"Enumerate every arrangement" sounds like a job for a dozen nested loops — appalling for `[1, 2, 3]`
(6 answers) and impossible by hand for `[1, 2, 3, 4, 5, 6, 7]` (5040 answers). Backtracking asks a
sharper question: _can I grow one candidate at a time, and give up on a branch the moment it is
provably useless_ — so every dead end is cut before its whole subtree is explored? The answer is the
choose–try–un-choose dance, and the cutting is called pruning.

## Start with an analogy

Organizing seven books on a shelf: for the first slot you try each candidate book and leave the rest
waiting; for the second slot you try each _remaining_ book; and the moment you realize a book is
already on the shelf, you simply skip it — no ceremony. When a shelf gets to the end, write down the
ordering, then pick the last book up and put it back, so the space is free for the next ordering.

That "put it back" is the un-choose. Without it, your second idea would start with the first
bookshelf already half-filled and every ordering would be nonsense.

## The decision tree

Think of the search as a tree. The root is the empty candidate. Each edge is one decision — "add
this book / this number." Each node is a **partial answer** (a prefix). Leaves are complete answers:
a full shelf, a full permutation, a finished subset.

- **Choose** — extend the current prefix with the next piece.
- **Try** — recurse; the child node explores every completion of that prefix.
- **Un-choose** — when the recursion returns, remove the piece, so the sibling branch starts from
  the _same_ prefix.
- **Prune** — before recursing, skip any piece that makes the branch provably invalid. This is what
  pens in the tree: one skipped node deletes its whole subtree.

## Subsets: every leaf accepted

Subsets is backtracking where pruning sleeps: since every subset is valid, the search simply visits
every node of the tree and records the current prefix at each one. With the "grow by any later
element" walk, the recorded nodes for `[1, 2, 3]` come out in a clean, repeatable order: `[]`,
`[1]`, `[1, 2]`, `[1, 2, 3]`, `[1, 3]`, `[2]`, `[2, 3]`, `[3]`.

That order is not random — it falls out of the un-choose rule. When you return from `[1, 2]` you
have `[1]` again, so the next sibling naturally becomes `[1, 3]`. A stable story for a stable
output.

## Permutations: pruning does the real work

Permutations demand every element appear exactly once. The search maintains a **used** marker; at
every level it loops the values in array order and prunes any value already used — the branch is
provably dead because a permutation with a repeated element is not a permutation. It only recurses
into fresh values, so the tree is instantly trimmed from n branches per node to n − depth, and the
leaves are exactly the n! permutations, in a canonical order.

## What this is NOT

| Misconception                             | Truth                                                                                                                                  |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| "Backtracking is brute-force enumeration" | Enumeration plus proof-based pruning: dead subtrees are cut _before_ descent, which is what separates it from a careless flat loop.    |
| "Un-choosing is an optional cleanup step" | It is load-bearing. Forget the pop and every sibling branch inherits the previous branch's elements.                                   |
| "Pruning is an optimization you can skip" | A wrong prune changes the answer; an absent prune re-explores a provably dead subtree. Both are real, and only the latter is safe.     |
| "Backtracking and DP are rivals"          | Backtracking explores alternatives; DP remembers repeated subanswers. Same tree, different trade — memoize when the same state recurs. |

## Why this matters for the rest of the trip

The pattern behind Subsets and Permutations is the engine beneath N-Queens, combinations, and
word-search style problems, and it leans directly on the recursion you studied on Day 7. The
discipline transfers far beyond enumeration: anytime you test a partial solution and walk it back,
you are doing the choose–try–un-choose dance. And when you notice the same partial states appearing
again and again, that is the signal to add a memo and let DP take over.

Solve the two problems above. Before you code, draw the decision tree for a tiny input and mark
which edge gets pruned — the tree is the algorithm; the code is just the tree in a loop.
