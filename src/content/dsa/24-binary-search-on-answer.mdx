## The one question this page answers

The usual binary search question is "where in this sorted array is my value?" This page answers a
deeper one: _what if the thing I am searching is not a value in an array at all, but a choice of
answer?_ Koko's problem is not "find a pile" but "find the smallest speed that fits in the time."
The leap is realizing that speeds form an ordered range, that "fast enough" is a predicate that
flips from false to true exactly once, and that binary search halves on that flip — O(n log range)
instead of trying every speed.

## Start with an analogy

A thermostat hunt. You know the room is too cold at 15° and too hot at 30°, and somewhere between
the perfect temperature flips from "too cold" to "too hot" — never back again. You do not try every
degree. You set 22°, feel the room, and throw away half the range: too hot means the answer is below
22°, too cold means it is above. Each trial halves the remaining degrees.

The degrees are the **answer space**, the too-cold/too-hot test is the **feasibility check**, and
the flip that never reverses is the **monotone predicate**.

## From sorted array to sorted answers

Binary search has always been about a monotone predicate. In a sorted array, `arr[mid] ≥ target` is
true at the target and everywhere after — a single flip. Koko's version is the same shape:

- The **search space** is speeds `1 .. max(piles)`, ordered from slow to fast.
- The **predicate** is `feasible(k) = sum(ceil(pile / k)) ≤ h`.
- **Monotonicity:** if speed `k` fits in `h` hours, every faster speed fits too — speeding up only
  removes hours. So `feasible` is `false, false, …, true, true`, and the answer is the first `true`.

## The search, step by step

1. `lo = 1`, `hi = max(piles)` — the answer is guaranteed to live in here (speed = max always
   works).
2. `mid = floor((lo + hi) / 2)`.
3. Compute `sum(ceil(pile / mid))`. If it is `≤ h`: `hi = mid` (mid works, maybe smaller works).
   Else: `lo = mid + 1` (mid is too slow).
4. Repeat until `lo === hi`; that value is the smallest feasible speed.

The visualizer runs the whole search for `piles = [3,6,7,11], h = 8`: mid 6 feasible → hi 6; mid 3
too slow → lo 4; mid 5 feasible → hi 5; mid 4 feasible → hi 4; lo meets hi at 4. Each halving
removes half the remaining speeds, and each check costs a pass over all piles: O(n log max(pile)).

## What this is NOT

| Misconception                                        | Truth                                                                                                                             |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| "Binary search needs a sorted array"                 | It needs a monotone predicate over an ordered space; the sorted array is one instance, the speed range is another.                |
| "Feasible answers are the whole range"               | They are a half-line — everything from the answer up. The job is to find the leftmost point of that half-line.                    |
| "The answer is the maximum feasible speed"           | It is the minimum; fast speeds trivially work, so the interesting boundary is the slowest speed that still fits.                  |
| "ceil(pile / k) is optional precision"               | Koko finishes a pile within the hour she starts it; rounding up is the entire model of time, and skipping it gives wrong answers. |
| "Binary search on answer is slower than brute force" | The brute force tests every speed (O(max × n)); the search tests O(log max) speeds, a colossal saving at large pile sizes.        |

## Why this matters for the rest of the trip

"Binary search the answer" is the Swiss army knife for minimax and feasibility problems: aggressive
cows, split-array-largest-sum, the smallest divisor, and capacity planning all fit the same mold —
find the boundary where a cheap predicate flips. It also completes a theme this track has been
building since binary search proper: make the world monotone, then halve. The habit to take away is
to ask, when a problem sounds like "minimize X such that Y is achievable", whether Y-as-a-predicate
is monotone in X — if it is, you are one binary search away from the answer.

Solve the problem above. Write the feasibility function first and test it by hand on `[3,6,7,11]` at
speeds 3, 4 and 5 before you trust the search — and then convince yourself why `hi = mid` (not
`mid − 1`) is correct when a probe is feasible.
