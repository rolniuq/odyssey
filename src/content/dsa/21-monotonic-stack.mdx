## The one question this page answers

For-each problems — "for every element, find the nearest neighbor that is bigger, smaller, hotter,
shorter" — look quadratic at first glance, because the naive way compares each element against every
later one. This page answers one question: _can a stack, whose only power is push and pop, answer
all of those neighbors in a single pass?_ The answer is yes, and the trick is one ordering rule:
keep the stack strictly decreasing (or increasing), so the top is always the one element worth
comparing against. That single rule turns "nearest greater element" into a stack that pops when a
bigger value arrives — and, because each element is pushed and popped once, the whole thing runs in
linear time.

## Start with an analogy

A climbing queue at a rope wall. Everyone waits in line, and the line is always ordered by skill:
the strongest climber at the front, the weakest at the back. A new person joins at the back. Anyone
at the back who is weaker than the newcomer steps out — they now have a stronger climber to follow —
and the newcomer takes the back spot. The line never grows without order: everyone weaker than the
new arrival leaves first.

The waiting line is the **monotonic stack**, ordered from strong (bottom) to weak (top). The
newcomer is the **current element**. The people who step out are the **pops**, and each one, as it
leaves, learns who outranks it — which is exactly the answer the problem wanted.

## The monotonic stack, defined

A monotonic stack is a stack whose elements always stay in sorted order from bottom to top — here,
**strictly decreasing** (each top is smaller than the one below). The push procedure enforces it:

1. While the top of the stack is **not in the right order** with the new element (for a decreasing
   stack: while `top ≤ new`), pop it.
2. Push the new element.

Because the invariant is restored before every push, the top of the stack is always the smallest
waiting element — the closest, most recent candidate. That locality is what removes the need to
scan.

## Daily Temperatures: the near pair, made local

For each day, find the number of days until a strictly warmer day. The stack holds indices of days
still waiting, ordered so temperatures decrease toward the top. For each day `i`:

- While `temperatures[i] > temperatures[stack.top]`, the warmer day has arrived: pop `top` and write
  `answer[top] = i - top`.
- Push `i`.

Days left on the stack at the end never find a warmer day: `0`. The visualizer above runs the whole
walk on `[73,74,75,71,69,72,76,73]` — watch day 6 (76°) answer two stale days at once, each with a
different wait.

**Cost:** every index is pushed once and popped at most once, so the pops are O(n) total — the
algorithm is linear, full stop.

## Largest Rectangle in Histogram: bounds from the neighbors

Now each bar wants its own rectangle, so a bar needs its **nearest shorter bar** on each side. The
same stack, this time kept increasing, finds both bounds as a side effect of popping:

1. Sweep left to right. When `heights[i]` is **shorter** than the top, the top has found its right
   bound at `i`; pop it, take the new top (or −1) as the left bound, and compute
   `area = heights[top] × (i − left − 1)`.
2. When the sweep ends, drain the stack with `i = heights.length`.

For `[2,1,5,6,2,3]` the max is 10 (the 5-and-6 pair). For `[6,7,5,2,4,5,9,3]` the max is 16 — the
whole array at height 2. The neighbor-finding pattern is identical to Daily Temperatures; only the
arithmetic you do at the pop changes.

## What this is NOT

| Misconception                                 | Truth                                                                                                                         |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| "A stack is only for parentheses"             | Stacks encode recency; ordering the contents makes each element answer its nearest relevant neighbor in O(1) amortized time.  |
| "Monotonic means the stack is sorted once"    | The invariant is restored before every push, so the ordering is guaranteed at every instant, not set up once at the start.    |
| "Each pop is O(1), so it is O(n) per element" | Each element pops at most once total; the sum of all pops is n, which is what makes the pass linear, not each pop's own cost. |
| "Daily Temperatures and Histogram differ"     | One algorithm: a monotonic stack of indices that pops when the order breaks; only the pop arithmetic (wait vs area) changes.  |
| "The stack must store values, not indices"    | Storing indices lets you compute spans (i − top); storing only values loses the positions every answer needs.                 |

## Why this matters for the rest of the trip

The monotonic stack is the "nearest neighbor in one pass" machine — it reappears in trapping rain
water, the stock span, next greater element in circular arrays, and sliding-window-maximum variants.
The habit it teaches is the deepest one in this track: find the invariant that makes a pairwise
comparison local, and the quadratic fear evaporates. When you see "nearest bigger / nearest
smaller," reach for a stack that stays ordered and ask what each pop learns as it leaves.

Solve the two problems above. Daily Temperatures is the pure nearest-warmer form; Largest Rectangle
asks the same stack to report each bar's horizontal bounds. Make sure you can say, for a popped bar,
exactly which two indices bound its rectangle and why.
