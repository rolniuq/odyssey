## The one question this page answers

The track ends the way it began: not with a new concept, but with composition. This page answers one
question: _can you solve a problem that needs two tools at once?_ Top K Frequent Elements needs Day
1 hashing for the counts and Day 10 heaps for the selection. Copy List with Random Pointer needs Day
6 linked-list surgery and the map-between-structures habit from Day 25. Two problems, no new theory
— only the proof that twenty-seven days of tools have become reflex.

## Start with an analogy

A classroom where every student owns zero or more marbles. Who are the top k collectors? You cannot
rank anyone before the ledger exists, so first you tally every marble in one sweep. Then you read
the ledger and keep only the k biggest totals, dropping the smallest total whenever a bigger one
shows up. Tally first, select second — never rank before you count.

A filing cabinet of records, each with a "related to" note referencing another record by its
position — sometimes forward, sometimes backward. To duplicate the cabinet faithfully you first make
a blank twin of every record, then copy the notes across. A map tells you which twin belongs to
which original, so even a note pointing to a record you have not reached yet still lands on the
right twin.

The marble ledger is the frequency hash map. The blank-twin step is "create all copies before wiring
random."

## Top K Frequent Elements: count, then select

The problem is two phases and the discipline is to never merge them.

1. **Count.** Walk `nums` once, tallying every value into a hash map — O(n), one update per element.
   Frequencies are the raw material; nothing about ranking happens here.
2. **Select.** Collect the distinct values with their counts. A min-heap of size `k` keeps the `k`
   largest counts seen so far, dropping the smallest candidate on every new element — O(n log k).
   Sorting the pairs instead costs O(m log m) for `m` distinct values; both are valid, the heap is
   the smarter choice for small `k`.

The result in the common case is decided by the tally: `[1,1,1,2,2,3]` gives counts `1:3, 2:2, 3:1`,
so the top 2 are `1` and `2`. Watch the visualizer fill the tally, then pick the top k.

## Copy List with Random Pointer: build copies first, then wire

The serialized input `[[val, randomIndex], ...]` describes a list whose `random` may point anywhere
— including ahead of the current node. That forward case is the entire trap.

- **Naive one pass fails:** copying node `i` and immediately wiring `random` fails when `random`
  targets node `j > i`, which does not exist yet.
- **Build then wire:** create one brand-new node per entry first, remembering each copy. Wire `next`
  in index order. Then, for each entry, point the copy's `random` at the copy built for
  `randomIndex`. Both directions resolve because every copy already exists.
- **Serialize back:** emit `[val, randomIndex]` per copy, reading `randomIndex` from the
  original-to-copy map in reverse.

This is Day 6 linked lists with a Day 25 map-as-glue: one structure stores the pairing so pointer
surgery stays O(n). The classic LeetCode variant (with `Node` objects) is the same algorithm; the
serialized contract here just makes the judge JSON-friendly.

## What this is NOT

| Misconception                                   | Truth                                                                                                                |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| "Top K is solved by sorting the original array" | Sorting values does not group by frequency; the hash-map tally must come first, then a heap or sort on the _counts_. |
| "Top K needs every element ranked"              | A min-heap of size k keeps only the candidates that matter — O(n log k), cheaper than a full sort when k is small.   |
| "Copy List means duplicating the values"        | The random pointer must be rewired to the twin nodes, not copied by value; shared values make value-copying wrong.   |
| "One pass can wire the random pointers"         | A forward random reference points at a node not yet created; every copy must exist before any random wiring happens. |
| "Review days introduce new theory"              | Every move in today's problems is an earlier day — hashing, heaps, linked lists, maps; only the combination is new.  |

## Why this matters for the rest of the trip

The final sprint is a mirror of the whole arc: Day 1 taught you to hash, Day 2 taught you to move
pointers, Day 6 taught you linked lists, Day 10 taught you heaps, Day 25 taught you to weld two
structures together — and today you did all of it in two problems. Real interview and engineering
problems are rarely one pure pattern; they are compositions like these. If you can look at a problem
and name both its counting phase and its selection phase — or notice that a copy needs to exist
before a pointer can be wired — you are no longer learning patterns, you are _using_ them. The track
is complete: twenty-eight days, one concept per page, and the habit, now, to explain any of it
simply.

Solve the two problems above. For Top K, write the count pass and the selection pass as two clearly
separated steps. For Copy List, resist the one-pass impulse — create every copy first, then wire,
and the forward `randomIndex` cases stop being special at all.
