## The one question this page answers

"Give me the kth largest" and "give me the k closest" feel like sorting problems: rearrange
everything, pick the kth. A heap asks a cheaper question: _can we watch only the top k the whole
time, throwing away any value that could never be in it?_ Yes — with a structure whose root is
always the current weakest of the best, inserts and evictions cost O(log k) each.

## Start with an analogy

A nightclub holding exactly k VIPs. The doorman keeps the door policy simple: the least famous
person currently inside stands at the door. When someone arrives, if they are less famous than the
doorman, they are turned away at once; if more famous, they walk in and the current doorman gets
bumped out. At any moment the person you can name as "the kth most famous" is standing at the door.

The doorman is the heap root. The club is the min-heap of size k: dropping the weakest member is
O(log k), and rejecting a nobody is O(1).

## The heap is a tree living in an array

A **heap** is a complete binary tree — every level full except maybe the last, filled left to right
— with one vertical invariant. In a **min-heap**, every parent is no larger than its children, so
the root is the minimum. Two moves keep that truth alive:

- **Sift up (insert):** append the new value as a leaf; while it is smaller than its parent, swap
  them. It rises until parent ≤ value.
- **Sift down (extract-min):** move the last leaf to the root; while it is larger than its smallest
  child, swap with that child. It descends until it is ≤ both children.

The trick that makes it cheap is storage: the tree is a flat array, children of index `i` are
`2i + 1` and `2i + 2`, and proof of "no pointers needed" is in the working code above.

Each sift is one root-to-leaf path, and a complete tree with n nodes has height about log n — hence
**O(log n)** insert and extract. Only the root is ever visible, which is all a priority queue ever
promised.

## Running top-k, the kth largest way

Keep a **min-heap of size k** as you scan the array:

1. Push the next value. If the heap exceeds k, evict the root (the smallest of the current k).
2. A value smaller than the root never enters the heap — it is below the current kth largest and
   could not belong to the top k.
3. When the array ends, the root IS the kth largest.

The diagram above replays `[3, 2, 1, 5, 6, 4]` with k = 3 — watch the weakest member get bumped and
the root always stay the answer-to-be.

## K closest, without a single sqrt

K Closest is the same trophy case with a twist: "distance from the origin." Since `x² + y²` grows
exactly as `sqrt(x² + y²)` does, ordering by the squared value is ordering by true distance — so no
square root ever runs. Sort ascending and slice the first k, or (when k is small) run the same
size-k structure keyed on distance. Let the k-to-n ratio pick the tool.

## What this is NOT

| Misconception                                     | Truth                                                                                                                    |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| "A heap is a sorted array"                        | Only vertical invariants hold (parent ≤ children); flat reads are unsorted, and that is fine — the root is all you need. |
| "Priority queue and binary search tree are twins" | A tree keeps the whole ordering navigable; a heap gives you one value fast and everything else costs you a sift.         |

| "Extract-min always removes the smallest value ever insterted" | It removes the current minimum of
the live set — values added since may be smaller yet still lose to the sift order. | | "K closest
needs Pythagorean distance computed" | Squared distance is monotone in distance, so it sorts
identically — sqrt is dropped without losing correctness. |

## Why this matters for the rest of the trip

The heap is your first real "keep a small window of the best" tool and the raw material of
Dijkstra's algorithm, Huffman coding, and the merge-k-sorted-lists family — every "always handle the
currently smallest/biggest" problem. Practicing a hand-rolled sift now (as the problem above
demands) means the built-in priority queues later are not a black box but a shortcut.

Solve the two problems above — and make sure you can run that size-k min-heap by hand on the small
arrays before you rely on it.
