## The one question this page answers

Some problems look like "do this to a whole thing", when they are secretly "do this to a smaller
thing, then do a little bookkeeping". Recursion asks: _can a function solve its own problem by
delegating to a smaller version of itself, trusting the smaller call, and combining the result?_ For
anything that can be defined in terms of itself — factorials, Fibonacci, tree walks — yes.

## Start with an analogy

A factory line where each worker builds a smaller box and hands it to the next worker. Worker #5
does not know how to build the whole box; they know that the box is "a lid, plus whatever worker #4
makes". Worker #4 thinks the same and passes to #3, who passes to #2, who passes to #1 — and worker
#1 has the base case: "the smallest box is just a base, no more nesting, done." Then the answers
climb back up. Every worker is a stack frame: someone waiting, someone below, one lid at a time
being locked on.

## Two parts, one contract

Every honest recursive function has:

1. **A base case** — an input so small you answer it directly. It is the exit door: no further call
   of yourself, just a return.
2. **A recursive case** — solve the reduced problem by calling yourself with a strictly smaller
   argument, then combine the answer with your own contribution.

Both must hold. Missing the base case means infinite descent. Missing the shrink means even a base
case can never be reached, because nothing moves toward it.

### The stack does the remembering

Every call — including recursive ones — pushes a stack frame with its own copy of the parameters.
The caller is not erased: it is frozen mid-computation, waiting for the child's return value. On the
way down, frames stack up; on the way up, each pops and returns its answer. That freeze/pop rhythm
is what "unwinding the stack" means.

### The factorial rehearsal

Factorial is recursion's hello world. As a python-style definition:

- base: factorial(0) = 1
- recursive: factorial(n) = n × factorial(n - 1)

`factorial(5)` chases down to `factorial(0) = 1`, then multiplies back up: 1 → 1 × 1 → 2 × 1 → 3 × 2
→ 4 × 6 → 5 × 24 = 120. Say it out loud once and the pattern — shrink, bottom out, multiply back up
— becomes permanent.

## The exponential trap, and the memo that dodges it

Fibonacci, written naively, is criminal:

- base: fib(0) = 0, fib(1) = 1
- recursive: fib(n) = fib(n - 1) + fib(n - 2)

Each call makes two children, so the call tree doubles at every level — O(2 to the n). The diagram
above shows the horror plainly: `fib(3)` and `fib(2)` appear twice. We are redoing identical work.

The fix is **memoization**: keep a map of argument → result. Check the map before recursing; store
into it after computing. Now every distinct n is computed once and every later request is a lookup —
exponential becomes linear. This one habit is the difference between climbing stairs instantly and
watching a small page spin forever.

## What this is NOT

| Misconception                | Truth                                                                                                                  |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| "Recursion is a faster loop" | It is a different trade: clearer problem decomposition, but stack frames and call overhead cost more than a flat loop. |

| "Recursion is just elegance — one can always use a loop" | Same power, yes — but the
shrink/base-case lens is often the clearest description, and trees (next days) are awkward as loops.
| | "A recursive call rewrites the same function" | Each call gets its own frame and its own
parameters; the caller genuinely pauses to await the child result. | | "Memoization makes recursion
memory-free" | It buys time by spending a map of size O(n) — a deliberate, visible memory-for-time
trade. |
