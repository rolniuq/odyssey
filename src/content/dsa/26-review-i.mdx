## The one question this page answers

Twenty-five days in, the question is not whether you can learn something new — it is whether you
still own what you learned first. This page answers one question: _can you pull two-pointer thinking
and sliding-window thinking apart, and apply each to a problem that twists it?_ Two pointers close
in on 3Sum; a window slides across Minimum Window Substring. The one-pass discipline from Days 2 and
3 is the entire engine of both — this time under harder constraints, with duplicate handling and a
validity check that must stay cheap.

## Start with an analogy

A long hallway with numbered doors. A trio of friends must find every set of three rooms whose
numbers sum to zero. They line the doors up in numeric order, then for each first door two friends
walk the rest of the hallway from opposite ends: sum too small, step in from the left; sum too big,
step in from the right; exact zero, note the trio and step both in. Every step retires an entire
region of hallway.

A second task: a very long banner reading `ADOBECODEBANC` and a stub of letters, `ABC`, to cover.
One edge of a curtain sweeps right until all three letters are hidden underneath it, then the other
edge sweeps right — closing in — while all three stay hidden. Each sweep reads any letter of the
banner at most twice: once when the curtain edge passes it, once when it is revealed.

The lined-up hallway is sorted 3Sum. The curtain is the sliding window. Both are one pass, two
indices, and a precise rule for when moving an index is safe.

## The two tools, side by side

Both tools are two pointers, and the difference is their motion.

- **Closing-in pointers** start at opposite ends of a sorted (or otherwise monotone) region and move
  toward each other. The rule that makes them fast is ordering: with a sorted array, moving `lo`
  right proves every pair through the old `lo` is too small, and moving `hi` left proves every pair
  through the old `hi` is too big. Each move discards a class of candidates. No ordering, no
  justification — that is the Day 2 contract.

- **The sliding window** has two pointers that both advance monotonically. The right edge grows the
  window until it satisfies some predicate, then the left edge shrinks it while the predicate still
  holds, then growth resumes. The window needs no sorted input; it only needs the validity test to
  be monotone under shrinking — the window is valid now, gets smaller, and we ask "still valid?".
  The cost is linear because each index is a right-edge arrival and a left-edge departure, each
  once.

3Sum is the first tool asked to be clever about duplicates; Minimum Window is the second tool asked
to track validity in O(1). The rest of this page is exactly those two pressures.

## 3Sum: the closing-in pass, deduplicated

For each first element `nums[i]`, the other two must sum to `-nums[i]`. Because the array is sorted,
the pair scan is the Two Sum II move from Day 2:

1. Sort a copy ascending.
2. For each `i` — skipping any value equal to the previous first element — set `lo = i + 1` and
   `hi = nums.length - 1`.
3. While `lo < hi`: if the three sum to zero, record the triplet and then step both pointers past
   any duplicates; if the sum is too small, `lo++`; if too big, `hi--`.

The complexity: O(n log n) for the sort plus n two-pointer scans of O(n) each — O(n²) overall, which
dominates the sort.

The duplicates are the pressure. First-element duplicates regenerate identical triplets, so they are
skipped up front. Pair duplicates inside a match are skipped the same way: after recording a
triplet, advance `lo` past equal values and `hi` past equal values, then step both once more. The
triplets come out sorted because the scan emits them with `nums[i] ≤ nums[lo] ≤ nums[hi]` by
construction.

## Minimum Window Substring: the push-pull window

The predicate is "the window contains every character of t, duplicates included." The naive validity
check — recount the window against t on every move — would cost O(n · |t|). The satisfied-count
avoids that:

- **Count t** into a `need` map, and note how many distinct letters it has.
- **Grow the right edge** into `s`. When a character's in-window count reaches exactly its required
  count, bump the satisfied-count.
- **When the satisfied-count equals the number of distinct letters**, the window is valid. Shrink
  the left edge while it stays valid, updating the best window, and decrement the satisfied-count
  whenever a character falls below its requirement.
- Repeat until the right edge exhausts `s`.

The cost is O(n): two edges, one pass each, O(1) work per character. Watch the visualizer run the
classic `ADOBECODEBANC` / `ABC` case — the window finds `ADOBEC`, loses validity when it drops the
A, regains it, and finally locks onto `BANC`.

## What this is NOT

| Misconception                                            | Truth                                                                                                                                    |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| "Two pointers and sliding window are unrelated tricks"   | The sliding window IS two pointers — the right edge grows, the left edge chases it; only the motion differs from closing in.             |
| "3Sum needs three nested loops"                          | After sorting, each first element runs one closing-in scan; every pointer move discards a whole region, so it is O(n²), not O(n³).       |
| "Duplicates make 3Sum harder"                            | They only make it _repeat_; skipping equal first elements and equal pair values keeps the answer unique at no extra cost.                |
| "Minimum Window re-checks the whole window each step"    | A satisfied-count over distinct letters turns each move into O(1) arithmetic; the window is valid the instant the count hits its target. |
| "The two problems belong to different days of the track" | Both are Day 2's one-pass, two-index discipline; Day 26 re-examines them because the same invariant powers harder variants.              |

## Why this matters for the rest of the trip

The review days exist to prove that the early tools were not memorized — they were understood.
Sliding window is the parent of subarray problems you have already met and will meet again; the
closing-in pointer is the heart of every sorted-array pair problem. If you can name, for any two
pointers, _what one move discards_, you have the invariant that carries you through both of today's
problems and most of the ones ahead. Minimum Window is also the canonical "two-pass, one-hash-map"
shape that reappears in Top K Frequent Elements at the finish line.

Solve the two problems above. For 3Sum, write the dedup in both places before you test — the triplet
record and the pair skip. For Minimum Window, write the satisfied-count version and confirm it
returns `BANC` on the classic input without ever recounting the window.
