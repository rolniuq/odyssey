## The one question this page answers

Arrays hand you everything instantly: any element by index, in one leap. A linked list asks a
sharper question: _if elements are permitted to live anywhere in memory, chained by pointers, what
do we give up — and what becomes suddenly cheap?_ The answer: you give up random access, but
insertion and deletion at a known spot become O(1), and a whole class of "pointer dance" algorithms
opens up.

## Start with an analogy

A scavenger hunt. You are given a first clue; it says only _where the next clue is_. You walk there,
read the next one, and onward. You can never "jump to clue 7" — nothing tells you where clue 7 is
until you stand on clue 6. That is the whole personality of a linked list.

An array is the opposite: a numbered row of lockers where locker 7 is seven slots down the hall from
locker 0, computed in one step. The hunt is a chain; the lockers are a slab of contiguous memory.

## Meet the node and the arrow

A node is the list's atomic unit — a value and one pointer, `next`. The last node points to `null`
(`None`, in Python terms), which is how a walker knows the hunt is over. Walking the list means
"start at `head`; follow `next` until it is `null`" — n arrows for n nodes, always O(n).

### The cost you pay

Because nodes live anywhere, "give me node at index k" requires walking k arrows from `head`. There
is no math that predicts address of node k. So **random access is O(n)**, and the familiar "array
.length" is also unavailable — you must count as you walk.

### The cost you gain

Inserting or deleting a node, given the pointer to its place, is a matter of splicing arrows:
`b.next = a.next; a.next = b` (insert), or `a.next = a.next.next` (delete). No shifting, no resizing
— O(1). That is why queues and caches pick linked structures.

## The reversal dance: three pointers

Reverse a list. The honest scalar version of the problem: rewire every arrow to point backward in
one pass, using O(1) extra space.

The move sequence is defensive:

1. `prev = null`, `curr = head`.
2. While `curr` exists: save `next = curr.next` — the only bridge to the rest of the list.
3. Flip the arrow: `curr.next = prev`.
4. Slide the trio: `prev = curr; curr = next`.

When `curr` falls off the end, `prev` is the new head. Watch the express-courier picture in the
diagram above: the "done" cells left of `curr` are the nodes whose arrows now point backward.

### Why the save is non-negotiable

Step 2 is the heart. If you flip `curr.next` before grabbing `next`, the remnant of the list hanging
off that arrow becomes unreachable — you have destroyed the very path your walker needs.
Save-then-flip is not a nicety; it is the invariant that keeps the loop alive.

## Cycle hunting: two walkers

A cycle is a bug where a tail node points back into the list, so the walk never ends. How do you
know, without visited-markers (which cost O(n) space)?

Floyd's tortoise and hare: send `slow` and `fast` off together; `slow` steps one node, `fast` two.
If the list is a line, `fast` reaches `null` first — no cycle. If there is a loop, the two are
trapped inside a finite circle, and because `fast` gains one node per step on `slow`, it must
eventually lap it and collide. Two variables, no markers: O(1) extra space.

## What this is NOT

| Misconception                                  | Truth                                                                                                                  |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| "A list is just an array with extra steps"     | Arrays own contiguous-memory random access; lists own splice-in-the-middle O(1) surgery. They are different contracts. |
| "Reversal means swapping around values"        | Reversal is pointer surgery on `next`, walking once; values stay exactly where they were allocated.                    |
| "Cycle detection needs a visited set"          | Floyd detects it with two walkers and O(1) space — the set is the naive O(n) answer.                                   |
| "Indexing a list is fine if you cache lengths" | Length or not, reaching index k still costs k arrow-hops; cached length only buys you `n`, not random access.          |

## Why this matters for the rest of the trip

Day 7's recursion clothes many "walk the chain" routines in a recursive costume (a base case at
`null`, a recursive case on `node.next`) — the reversal above, for instance, is a one-line recursive
cousin. And the pointer-rewiring habits pay off on Day 8-10 as trees — those are just lists with two
arrows per node — and on heap-style problems where "keep only the k best" needs a small helper
structure.
