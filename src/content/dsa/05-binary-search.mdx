## The one question this page answers

You have a sorted list and a target. The lazy read is to walk the list comparing until you find it —
**O(n)** for one look-up, and O(n) again for the next. Binary search asks: _can one comparison
between the target and a single element rule out a whole side of the list?_ Because the list is
sorted, yes — and the price drops to **O(log n)**.

## Start with an analogy

The children's game "guess my number between 1 and 100". You do not guess 1, 2, 3… up the line; you
guess 50. Too high? Everything above 50 dies at once. Too low? Everything below dies. The next guess
splits whatever survives, and within a handful of guesses you own the number — because every answer
discards half the remaining range in one move.

The list is the range, `lo` and `hi` are its edges, and each guess is the midpoint.

## The invariant and the cut

The rule to repeat out loud: **the target, if it is in the list at all, lives inside `[lo, hi]`**.
That invariant is the whole algorithm. While `lo <= hi`:

1. Read the midpoint `mid = (lo + hi) / 2` (integer).
2. `nums[mid] === target`? Return `mid`.
3. `nums[mid] < target`? Every value at or left of `mid` is too small — set `lo = mid + 1`.
4. Otherwise every value at or right of `mid` is too big — set `hi = mid - 1`.

When `lo` overtakes `hi`, the invariant is empty, and the honest answer is `-1`.

### Why the discard is never a mistake

Sorted order makes the discard monotone: if the middle value is smaller than the target, then
everything to its left is smaller still — none of them can be the target, so dropping them proves
nothing. Same on the other side. Each step throws away half the range without looking at it, which
is why the loop runs `log₂(n)` times and not `n`.

### The rotated twist

A rotated array (sorted, then moved at some pivot, e.g. `[4,5,6,7,0,1,2]`) is not sorted globally —
but it is sorted in **two ascending runs**, so at every step at least one side of `mid` is a normal
sorted half. The refined loop checks which side that is (compare `nums[mid]` against `nums[hi]`),
then uses ordinary sorted bounds to decide whether the target could be inside it:

- right half sorted: `nums[mid] < target ≤ nums[hi]`? search right; else left,
- left half sorted: `nums[lo] ≤ target < nums[mid]`? search left; else right.

Same halving, one extra branch to find the sorted side first. Distinct values guarantee the "at
least one sorted half" property cleanly, which is why the classic problem states them.

## What this is NOT

| Misconception                                               | Truth                                                                                                                              |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| "Binary search finds things faster by luck"                 | It works because ordering makes the discard provable, not because of lucky guesses.                                                |
| "It requires the array to be indexable AND already ordered" | Ordered, yes — and random access, yes. That is the price of log n; a linked list can never binary-search without a jump structure. |
| "It keeps the whole range until the very end"               | It deliberately throws away halves as it goes; only `[lo, hi]` ever remains live.                                                  |
| "Rotated search needs a different algorithm"                | It is the same binary search plus one branch that locates the still-sorted half before applying normal bounds.                     |

## Why this matters for the rest of the trip

Binary search is the starting pistol for a whole class of "guess an answer, then verify" problems:
finding the smallest feasible value, square roots by search, and "peak index" problems all reuse the
halving rhythm. And the shape recurs constantly in the trees days — a binary search tree is binary
search applied at every node. Master the `[lo, hi]` invariant now and every one of those later pages
gets cheaper.

Solve the two problems above before moving on — then try _Find First and Last Position of Element in
Sorted Array_ and _Find Minimum in Rotated Sorted Array_ on LeetCode to turn the rhythm into reflex.
