## The one question this page answers

You have already walked past a value, and later you need to know _whether that exact value was in
the past — and where_. The naive answer is to re-scan everything you have seen every time you need
to know, which for Two Sum means a nested loop: for each `i`, check every `j`. That is **O(n²)**.
The hash map asks a sharper question: _can the past be organized so "did I see this already?" is one
poke instead of a scan?_ The answer is yes — at the price of some extra memory.

## Start with an analogy

A coat-check counter in a crowded hall. When you hand over your coat you get a ticket, and when you
come back you do not describe your coat to every attendant (`"dark blue, three buttons?"`) as you
would if you were scanning a rack. You hand over the ticket and get the coat back in a step, because
the ticket is a key tied to the coat's spot.

The hash map is that ticket desk. Every value you have met gets a peg ("slot") of its own, computed
from the value itself. Saying "have I seen a 7?" means walking to peg 7 — not walking the whole rack
of past values.

## The pegboard is a hash table

A hash map stores `key → anything`. The key is the value you will later ask about; the peg it lands
on is produced by a hash function, so the same key always lands on the same peg. In practice a peg
is a _bucket_ that may hold a couple of keys (that is the "collision" that makes O(1) only
_expected_), but with a decent hash the bucket stays tiny. Lookup, insert, and delete are each a
poke: O(1) expected.

### The complement trick

Two Sum does not search for a pair; it searches for a _memory_. For each value `nums[i]`, the
partner we need is `target - nums[i]`. Instead of scanning ahead for it, we check whether that
complement is already on the pegboard:

1. Not on the board? Hide this value on its peg (`value → index`) and keep walking.
2. On the board? The plural is found: `[board.get(complement), i]`.

The map only holds the **left side** of the journey — everything seen so far. That is enough,
because whichever element is the pair's _second_ member will find the first one waiting on its peg.

### Set versus Map

The `Set` is the map stripped to the question "is this key here?" — it stores buckets with no
slotted value. Contains Duplicate asks exactly that, so a `Set` is the minimal, honest tool: drop
each number in; if it is already there, duplicates exist.

## The honest cost ledger

The nested loop is O(n²) time and O(1) space. The hashed one-pass is O(n) time and O(n) space — one
peg per element. For array-sized inputs that trade is almost always a steal: an extra pass of memory
turns quadratic time into linear time, and the problems this unlocks (counting frequency, marking
seen, pairing complements) are constants of the algorithmic world.

## What this is NOT

| Misconception                             | Truth                                                                                                             |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| "Hashing is sorted access"                | A map gives membership and look-up; it does not order its keys. Sorting is a different tool with O(n log n) cost. |
| "Expected O(1) is guaranteed O(1)"        | Colliding keys share a bucket, so adversarial input can stretch a chain; 'expected' is the honest word.           |
| "A Set replaces an array"                 | Arrays keep order, allow index math, and cost nothing to store; a Set is membership-only.                         |
| "The complement trick needs sorted input" | No — it works on any order, which is why it beats two pointers (Day 2) on unsorted arrays.                        |

## Why this matters for the rest of the trip

Hashing is the memory layer under almost everything ahead. The sliding window (Day 3) uses a set of
seen characters to know when a window turned invalid; frequency counting shows up in anagrams and
grouping problems; and when you meet problems like _Group Anagrams_ or _Top K Frequent Elements_,
the reflex "what should each peg remember?" is how you pick the right side table.

Solve the two problems above before moving on — then try _Valid Anagram_ and _Intersection of Two
Arrays_ on LeetCode to make the peg reflex automatic.
