## The one question this page answers

Lists had one arrow per node and were walked in a line. A binary tree gives every node **two**
arrows — left and right — so the "line" becomes a folding structure, and the question becomes: _how
do you describe work over a whole tree, when the tree itself is described as "a node plus two
smaller trees"?_ The answer: recursively, with the null children as the exit doors.

## Start with an analogy

A family tree drawn upside down: one person at the top (the root), and beneath them two slots for
children, each of whom has two more, and so on. "Count how many people are in this family" is a
question you answer by asking each child to count their own branch and adding yourself. Nobody
counts the whole tree at once — every person counts their little triangle and reports up.

That is the recursive mindset: fish in the shape of the data structure.

## Read a tree from an array

Since the sandbox has no tree class, the problems hand you the tree as a **level-order array**:
`[3, 9, 20, null, null, 15, 7]` means root `3`, children `9` and `20`; `9` has two missing children
(the `null, null`); `20` has `15` and `7` as children. Reading order is level by level, left to
right, and `null` fills an absent slot — so its would-be children are skipped in the same pass.

Building it back is index discipline: claim the next two slots as children of each node in order.
When a node is null, its two slots are still consumed — which is why, after `9` and its two nulls,
the values `15, 7` land under `20`, not under `9`.

## The recursive contract for trees

Every tree operation follows the same two-part rhythm:

1. **Base case:** the node is `null` — no value, no children, answer is trivial (0, or "nothing
   here").
2. **Recursive case:** solve it for the left subtree and the right subtree, then combine with what
   the current node contributes.

### Depth: 1 + the best child

Maximum depth is the canonical case. `depth(null) = 0`. For a real node, the answer is "one for
myself, plus the deeper of my two children":

```
depth(node) = 1 + max(depth(node.left), depth(node.right))
```

It bottoms out at the leaves: a leaf reports max(0, 0) + 1 = 1, its parent reports 2, and the number
that surfaces at the root is exactly the number of levels.

### Invert: swap left and right, then recurse

Inversion is the same rhythm with a swap in the middle:

1. If the node is null, do nothing.
2. Swap `node.left` and `node.right`.
3. Invert both children — that is, recurse.

Because the rule is applied at every node, the whole tree becomes its mirror image; the diagram
above walks the level-by-level swap. Notice the "What this is NOT" warning: reversing the level
order array would give different, wrong trees — child placement is what changes, not the sequence of
values.

## What this is NOT

| Misconception                                | Truth                                                                                                                        |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| "A tree is just a sorted list with branches" | Nothing is sorted unless you enforce a binary-search invariant; branches change which neighbors a node has, not an ordering. |
| "Inversion means reversing the array"        | Inversion swaps subtrees through a recursion; array-reversal scrambles positions and yields wrong mirrors.                   |
| "Depth counts edges"                         | As defined here it counts nodes along the path (LeetCode convention); being crisp about nodes vs edges prevents off-by-ones. |
| "Every node must have two children"          | A node may have 0, 1, or 2; nulls are legitimate, and a one-child (degenerate) chain is just a linked list in disguise.      |
