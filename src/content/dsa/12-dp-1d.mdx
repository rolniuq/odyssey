## The one question this page answers

Some questions feel like they ask "what is the single best plan?" — and the naive answer, _try every
plan_, explodes in your face. Dynamic programming asks a cheaper question: _can I write down the
answer to a smaller version of the same question, and then build the bigger answer from those
smaller answers?_ For the street of houses, the "smaller version" is "the best loot using only the
first i houses." Answer that for every i once, and the final i answers the whole street.

## Start with an analogy

A curator hangs paintings in a long gallery, one per wall, and must maximize total value — but never
two paintings on adjacent walls (the guards get confused). The naive curator enumerates every subset
of walls: exponential. The DP curator does something quieter: they walk the gallery and, at each
wall, write on a card "best value achievable using up to and including this wall." At wall 3 the
card says: _either we skipped wall 3_ (then the best is card 2) _or we hung it_ (then wall 2 is
forbidden, so the best is card 1 plus this painting's value).

Each card is built from two earlier cards. No plan is ever enumerated — just combined. The gallery
is your array, and the cards are the `dp` table.

## The three ingredients

Every DP is three things, named before any code:

1. **State** — what a cell means. Here: `dp[i]` = best loot among houses `0..i` under the rule.
2. **Transition** — how a cell derives from smaller cells. `dp[i] = max(dp[i-1], dp[i-2] + nums[i])`
   — skip house `i`, or rob it and add the best of two houses back.
3. **Base case** — the cells you fill by hand. `dp[0] = nums[0]`, `dp[1] = max(nums[0], nums[1])`.

Watch the visualizer fill `[2, 7, 9, 3, 1]` → `[2, 7, 11, 11, 12]`. Every cell is one `max` over two
answers that already exist — O(n) time, O(n) space.

## Coin Change: the table indexed by amount

Coin Change is the same machinery with a different ruler. "What is the best loot among the first i
houses" becomes "what is the fewest coins to make amount i?" — so the state is the amount, and the
table is indexed `0..amount` instead of by prefix.

Transition: `dp[i] = min over coins c of (dp[i - c] + 1)`. Base: `dp[0] = 0`. Everything else starts
at **Infinity** — the sentinel for "not possible yet." Fill ascending so every `dp[i - c]` is
already final, and when you finish, `dp[amount]` is the answer — or `-1` if it survived as Infinity.

The recurrence reuses coins freely because the state forgets which coin was used last. That is what
"unbounded" means here, and it is why the greedy habit fails while DP does not: DP tries every
denomination at every amount instead of committing to one.

## What this is NOT

| Misconception                                | Truth                                                                                                                            |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| "DP is recursion with extra steps"           | Recursion decomposes; DP _orders_ the computation so each subanswer is computed exactly once and reused. The table is the point. |
| "The table just stores intermediate results" | It stores the answers to _subproblems of the same shape_ — each cell answers a smaller version of the original question.         |
| "Any fill order works"                       | Cells must be filled so every dependency is already final. Amount tables go ascending; a wrong order reads garbage.              |
| "dp[1] can use the main recurrence"          | It would read dp[-1]. One-indexed bases are a real edge case — handle them by hand before the loop, or by padding the table.     |

## Why this matters for the rest of the trip

This page's three ingredients are the same three you will use for every DP that follows: tomorrow
the state gains a second dimension (two strings, a grid); later it becomes shortest paths and edit
distance. The skill that transfers is not the table — it is the act of naming a state, writing the
recurrence, and checking the bases. Do that, and the fill order and the loops write themselves.

Solve the two problems above. For each, write down the three ingredients _before_ writing a single
line of code — that discipline is worth more than the solutions.
