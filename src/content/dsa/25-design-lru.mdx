## The one question this page answers

Caches work by predicting the future from the past: the entry you used recently is the one you will
likely use next. This page answers one question: _can you honor that prediction with constant-time
operations, even while the cache forgets its oldest entry?_ The answer is the LRU design — and the
trick is that no single data structure can do it. A hash map finds things instantly but remembers no
order; a doubly linked list remembers order but finds nothing quickly. The design that works is both
at once, sharing one invariant, so eviction becomes a pointer shuffle instead of a scan.

## Start with an analogy

A desk with room for two reference books. Each time you use a book, you move it to the top of the
stack on your desk; the book at the bottom of the stack is the one you have not touched in the
longest time. When a third book arrives and the desk can hold two, the bottom book goes back to the
shelf. You never hunt for a book — you know the top of the stack — and you never shuffle the whole
pile; each use only reorders the two books.

The stack of books is the **doubly linked list** (recency order), your memory of where each book is
is the **hash map** (O(1) lookup), and the book sent to the shelf is the **least-recently-used
eviction**.

## The two halves, and why neither alone suffices

- **The hash map** (`key → node`) answers "does this key exist, and where?" in O(1). But a hash map
  has no order — it cannot say which key is oldest.
- **The doubly linked list** keeps recency order, least-recent on one end, most-recent on the other.
  But finding a key in a list is a walk, O(n).

The synthesis: the map stores **pointers to list nodes**, so a lookup finds the node, and the node
knows its own neighbors — unlink and re-link in O(1). Head and tail sentinels remove every
empty-list special case. Watch the visualizer above run capacity-2 cache through the classic
LeetCode sequence: you can see the evictions (key 2, then key 1) and the reordering on every hit.

## The operations

- **get(key):** look up the node in the map. If missing, return −1. If present, unlink the node and
  splice it at the most-recent end; return its value.
- **put(key, value):** if the key exists, update its value and move its node to the most-recent end.
  Otherwise, if the map is full, evict the least-recent node (the one after the head sentinel) —
  delete it from the map too — then insert the new node at the most-recent end.

Every step is a bounded pointer rewrite plus one map operation: **O(1)** per call, no scans, no
sorts. The price you pay is O(capacity) memory and the discipline to never let the map and the list
disagree.

## What this is NOT

| Misconception                      | Truth                                                                                                                            |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| "LRU just means delete the oldest" | It means delete the least **recently used**; an old key that gets touched every minute survives while an untouched new key goes. |
| "A single structure is enough"     | The map gives lookups but no order; the list gives order but no lookups. The design is the pair and its shared invariant.        |
| "Doubly linked = doubly expensive" | The second pointer is what lets a middle node remove itself in O(1); without it, deletion walks the list.                        |
| "get should not change anything"   | A read is a use. Successful gets must move their node to the most-recent end, or "recently used" stops meaning anything.         |
| "LRU is only a LeetCode problem"   | It is the cache policy of databases, OS page replacement, and web caches — the same map-plus-list shape appears in production.   |

## Why this matters for the rest of the trip

This is the capstone of the design mindset the track has been building: know what each structure is
good at, combine them so each covers the other's weakness, and guard the invariant that keeps them
consistent. The map-plus-list pattern recurs everywhere — LFU caches, eviction layers, frequency
counters — and the "design problem" shape (state + O(1) operations) is a whole interview category of
its own. More than any single algorithm, this page teaches you to think in pairs: one structure for
fast access, one for fast ordering, welded together by a shared pointer.

Solve the problem above. Write the two sentinels and the node class first, then implement
move-to-tail and evict-from-head as pure pointer surgery, and only then wire the map in. And trace
the full example by hand — the answer your runner expects is exactly the sequence the visualizer
played.
